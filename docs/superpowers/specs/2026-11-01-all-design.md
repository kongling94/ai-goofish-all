# ai-goofish-all 首版设计

日期：2026-11-01。目标仓库：https://github.com/kongling94/ai-goofish-all 。当前为空仓库，已确认可写。用户已选择“统一仓库、一个 Docker Compose 项目、统一管理入口，先跑通数字商品闭环”。本文供首版范围确认，尚未实施产品代码或修改 NAS。

## 1. 目标与范围

以 Usagi AI Goofish 的 Vue 3 + FastAPI 作为主应用，保留采集、分析、价格历史与任务管理。整合卖家能力，完成：自有数字商品目录 → 素材 → 发布 → 商品 ID 与规则绑定 → 买家咨询回复 → 已付款订单数字交付 → 有库存时自动续售。

“统一入口”意味着新增业务页面进入主应用的导航和登录流程，不是仅把两个原管理页面链接到一起。首版内部使用两个服务，避免把卖家系统的数万行事件循环直接搬进监控进程。

市场监控结果只生成选品候选，必须映射到用户自己的数字商品 SKU、库存和交付内容后才能发布。首版不自动购买别人的商品，不把抓取价格当作自有进货成本。

## 2. 已选择的方案与取舍

- 采用：一个仓库、一个 Compose、统一 Vue 界面，主 FastAPI 承担桥接和管理 API，GuDong 卖家引擎作为内部服务。保留现有能力，只开发统一入口、映射和流程衔接。
- 暂不采用：首版直接把两个后端、数据库和前端彻底重构成单进程。GuDong 的 reply_server.py 与 XianyuAutoAsync.py 合计约 3.4 万行，首版全部迁移会扩大协议、登录和订单处理的回归范围。
- 不采用：同时运行 23Star、GuDong 和 CredentialsBot 接管同一账号。避免重复回复与交付。

## 4. 仓库与运行结构

主目录沿用 Usagi：src/、web-ui/、tests/、prompts/、Dockerfile。按原 API → services → domain → infrastructure 分层新增整合模块，不另引入新 Web 框架。

vendor/xianyu-auto-reply-fix/ 保存固定版本卖家源码，排除 .git、账号数据、真实 .env、缓存、日志和其他运行数据。保留上游许可、源码及必要构建资源。新增 THIRD_PARTY_NOTICES.md、上游版本清单和维护说明。

Compose 两个服务：

1. all-app：Vue 静态资源 + 主 FastAPI + 桥接逻辑，仅这个管理入口映射宿主机端口。
2. seller-engine：卖家监听、发布、回复和交付；仅通过内部网络被 all-app 访问，默认不映射管理、VNC 或调试端口。

主应用与卖家引擎各自拥有自己的 SQLite 和持久化目录；只有所属服务写入对应数据库。跨服务通过 API，不让进程共同编辑同一个数据库。

## 5. 首版统一管理页面

保留：监控概览、采集任务、监控账号、结果、价格趋势、运行日志、AI 设置。

新增：

- 整合概览：卖家连接、运行模式、待发布、库存、订单、暂停原因。
- 商品目录/素材：自己的 SKU、标题、描述、图片、价格、交付方式和库存关联；监控候选可转为待补全素材。
- 发布管理：预览、单件发布、发布记录、未知结果核对、新商品 ID。
- 客服：账号/商品的关键词和 AI 回复设置、人工接管状态；使用已有卖家规则引擎。
- 数字库存与发货：卡密内容/库存、商品与交付规则对应、交付记录；敏感交付内容不进入普通日志。
- 订单与续售：订单同步、发货状态、续售开关、最低库存、等待时长及异常事件。
- 卖家账号：官方登录交互或用户自行导入登录态；不把账号 Cookie 暴露给无关页面或写入 Git。

首版优先完成能贯通上述流程的必要字段和操作，其他上游高级运营功能留在内部维护范围，不为补齐每个上游按钮而扩展界面。

## 6. 身份、AI 与密钥

浏览器只调用 all-app，卖家引擎的服务端认证由 all-app 管理。统一入口需在服务端验证会话，不能只依赖前端路由是否显示已登录。引擎认证失败不被误报为闲鱼账号失效。

监控 state JSON 与卖家 Cookie 字符串分别管理，保存显式账号映射；不自动同步或覆盖它们。首版面向单用户、小规模使用，不新增多租户平台。

DeepSeek 作为默认兼容接口选项，Key 由用户自行配置。监控分析和卖家 AI 回复配置分别持久化；未经用户选择不把现有 NAS Key 复制到新服务。示例文件没有真实密钥，日志只记录是否配置。

## 7. 数据与接口

主应用新增的 API 使用 /api/commerce/ 前缀。实际文件命名遵循现有仓库分层；不为仅用一次的简单逻辑提前创建抽象基类。

核心记录：

- Product：自有 sku、title、description、images、category、price、delivery_type、inventory_ref、status。
- Listing：sku、seller_account_id、material_id、publish_log_id、seller_item_id、status、last_error。
- AccountMapping：monitor_account_ref、seller_account_id；可以只绑定一侧。
- Execution：业务动作、对象 ID、运行模式、结果和时间；不保存 Cookie 或卡密明文。

监控结果通过现有 /api/results 系列读取。通知 Webhook 可作为后续事件入口，但不作为唯一可靠的商品数据源。

复用卖家端：/product-materials、/product-publish、/product-publish/batch、/publish-logs、/api/auto-relist/rules，以及已有商品回复、卡券和订单 API。适配层先核对当前固定版本真实 schema，接收外部输入时校验一次，内部使用已确定类型。

## 8. 发布闭环

流程：候选/手动建商品 → 补全自有素材、售价和库存 → 可发布 → 发布中 → 已发布/失败/待核对 → 绑定回复与交付规则。

来源商品 ID 与 seller_item_id 不混用。重复点击或重复候选不能导致同一 SKU 在同一账号下意外重复刊登；需要重复刊登的业务由续售规则明确触发。

发布请求已提交但返回丢失时，标记待核对，查询已有发布记录与在售商品，不因超时自动再发一遍。一个批次内串行不被宣传为全系统限速。

## 9. 回复、数字发货和续售

回复复用已有关键词/AI 引擎及人工接管，不重写消息协议。AI 不能自行生成未配置的卡密、库存承诺或超出商品规则的优惠。

数字发货复用卖家端库存、规则和付款事件。首版支持固定文本和库存卡密；任意供应商 API 取货、可视化流程编辑器不纳入首版必交付。

订单重放、应用重启与发送中断需要对应的交付记录与待核对状态；不能把“发送失败”直接当作“库存从未消耗”。付款、退款、取消等状态依照既有卖家实现核验后再触发。

续售只启用上游已存在的有条件流程：有库存、相关订单发货完成、原商品确认不在售、达到等待时长；保存新 ID 并迁移回复/交付关联。未知结果等待核对。

## 10. 运行模式与账号保护

首次启动默认演练模式，能走商品和接口适配流程，但不向闲鱼发布、不向买家发消息、不交付库存。演练闸门必须在卖家引擎启动和账号任务恢复之前生效，不建立真实闲鱼账号会话或消息监听；使用隔离的演练数据与受控平台边界，不修改真实库存。上游 Compose 中 AUTO_REPLY_ENABLED/AUTO_DELIVERY_ENABLED 是否被业务实际读取尚未验证，不能只设置这些环境变量就视为已阻断真实动作。演练验证与真实交易验收分别报告。平台执行必须由管理员显式切换为正式模式，并对目标账号启用对应动作。演练结果与真实成功分开显示。

暂停后停止新任务派发；遇到已识别闲鱼验证、HTTP 403/429 或登录失效时，将相关账号置为待人工处理，不自动过验证码，不通过账号轮换继续当前动作。已发出的平台请求可能返回未知结果，需要核对，不能承诺撤回已完成动作。

现有监控全局单任务策略继续保留。监控与卖家引擎之间不因各自有队列就宣称拥有统一请求预算；首版须在 UI 显示各自运行状态，并在同账号监控采集期间不派发新的发布批次。卖家实时订单/消息仍需各自处理，完整的跨所有内部 HTTP 请求调度不是首版隐含承诺。

上游不需要的擦亮、自动评价、求花、全量同步定时任务及自动更新默认关闭；只启用首版明确使用的监听、回复、交付和续售路径。具体开关与启动入口需在实现计划中逐项定位。

## 11. 本轮不纳入的功能

- 任意来源商品全自动搬运、自动采购、一件代发和实物打单揽收。
- 任意商品的原 ID 恢复上架/定时下架；不能用续售冒充该能力。
- 修改在售商品标价。价格趋势属于只读监控，真正自动降价需后续接入改价执行器及成本边界。
- 多执行引擎同时处理同一账号。
- 自动破解/代做验证，或任何免封承诺。
- 直接覆盖 NAS 现有服务或迁移现有账号数据；新仓库先通过独立验证。

这些缺项记录到路线图，不能在 README 或界面上标记为已经完成。

## 12. 实施阶段和验收

A. 基础导入：主项目、固定卖家源码、来源/许可、环境示例、双服务 Compose。验证无秘密、构建和健康检查；不以仅能 docker compose config 代替容器实际启动。

B. 核心后端：卖家客户端、身份边界、商品目录、映射、发布预览/执行与记录。使用实际数据库和本地可控 HTTP 测试服务；平台 API 不可用时只替代外部边界，不把业务逻辑复制到测试。

C. 统一前端：商品、发布、客服、库存和订单的最小必要页面，构建前端源码生成产物；不手改 dist/static 生成文件。

D. 数字闭环：配置固定内容/卡密、付款事件交付、重复事件、发送中断、库存耗尽、退款取消、续售和关联迁移；在演练模式验证全流程。

E. 发布与交接：提供真实支持的功能矩阵、安装/升级/回滚、备份和已知限制；代码审查、相关测试与构建通过后推送到用户仓库。真实账号测试、正式发布或真实订单交付单独由用户启动。

必要验收：

- 服务不可用/鉴权失败：页面明确错误，不显示发布成功。
- 缺图片、价格或库存：仅入口校验阻止，不触发平台写操作。
- 重复提交和平台结果未知：不意外重复发布。
- 商品发布成功但规则绑定失败：保留真实新 ID 与未完成步骤，不能重新发布掩盖绑定失败。
- 卡密耗尽/交付中断/订单重放：不会再次随意扣库存或重复交付。
- 原商品仍在售、退款取消、库存不足：不触发续售。
- 演练模式、暂停和验证异常：阻止新的相应外部动作。
- 新容器不会占用现有 NAS 服务端口或写入原服务数据目录。

## 13. 实现者可自行决定的细节

在现有框架内决定新模块的精确文件划分、表字段索引、页面组件拆分与错误文案。遇到上游接口能力缺失，先记录实际证据和受影响范围，再决定最小补丁；不因假设中的极低概率情况增加复杂保护。

根仓库初始化、提交和推送属于本次建库范围；不强推或覆盖已有远端提交。NAS 部署和真实账号接入不属于本轮默认动作。

设计复核：已由独立实现视角检查；补充演练启动边界后，没有仍必须由用户决定的重要问题。
